# Diagnose — 纪律性调试

用于解决复杂 bug 和性能问题。不做无意义的猜测，必须先建立可复现的反馈循环再动手。

**适用场景**：
- tester Agent 修正 3 轮仍未通过的问题
- 非确定性 bug（偶发、竞态条件）
- 性能回归
- 多模块交互导致的复杂问题

**不适用**：
- 简单 bug（直接让 dev Agent 修复即可）
- 编译错误（直接修，不需要诊断）

## Phase 1 — 构建反馈循环

**这是核心能力。** 如果有一个快速、确定性、可运行的 pass/fail 信号，你就能找到根因。如果没有，盯着代码看也没用。

在这里投入不成比例的精力。**要激进。要有创造力。不要放弃。**

### 构建方式（按优先级尝试）

1. **失败测试** — 在能触及 bug 的任何层面写一个失败的测试
2. **HTTP 脚本** — 用 curl 调用 dev server，断言响应
3. **CLI 调用** — 用 fixture 输入运行，diff 输出和预期
4. **无头浏览器脚本** — Playwright / Puppeteer 驱动 UI，断言 DOM/控制台/网络
5. **重放捕获的 trace** — 保存真实的网络请求/事件日志，重放代码路径
6. **一次性 harness** — 启动最小子系统，单个函数调用触发 bug
7. **属性/模糊测试** — 如果 bug 是"有时输出错误"，跑 1000 个随机输入
8. **二分 harness** — 如果 bug 出现在两个已知状态之间，用 `git bisect run` 自动化
9. **差分循环** — 同一输入跑旧版 vs 新版，diff 输出
10. **人工辅助脚本** — 最后手段。如果必须人工操作，用脚本驱动人工流程

### 迭代循环本身

把循环当作产品来优化：
- 能更快吗？（缓存 setup、跳过无关初始化、缩小测试范围）
- 信号更清晰吗？（断言具体症状，而非"没崩溃"）
- 更确定吗？（固定时间、种子随机、隔离文件系统、冻结网络）

30 秒的 flaky 循环比没有好不了多少。2 秒的确定性循环是调试超能力。

### 非确定性 bug

目标是提高复现率，而不是 100% 复现。循环触发 100 次、并行化、加压力、缩小时序窗口、注入 sleep。50% 概率的 bug 可调试，1% 的不行。

### 真的无法构建循环时

明确停下来告诉用户。列出尝试过的方式。请用户提供：
(a) 能复现的环境访问权限，(b) 捕获的产物（HAR 文件、日志 dump、core dump），(c) 添加临时生产探针的权限

**在没有循环之前，不要进入 Phase 2。**

## Phase 2 — 复现

运行循环，确认 bug 出现。

- [ ] 循环产生的是**用户描述的**失败模式 — 不是附近碰巧出现的其他失败
- [ ] 失败可跨多次运行复现（或非确定性 bug 的复现率高到可调试）
- [ ] 已捕获确切症状（错误消息、错误输出、慢耗时），后续阶段可验证修复

**复现不了就不继续。**

## Phase 3 — 假设

在测试任何假设之前，生成 **3-5 个排序假设**。单假设会锚定在第一个看起来合理的想法上。

每个假设必须**可证伪**：陈述它的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重"

无法陈述预测的假设是感觉 — 丢弃或锐化。

**将排序列表展示给用户再测试。** 用户通常有领域知识可以瞬间重新排序，或知道已排除的假设。

## Phase 4 — 探测

每个探针对应 Phase 3 的一个具体预测。**一次只改变一个变量。**

工具优先级：
1. **调试器 / REPL** — 一个断点胜过十条日志
2. **边界处的目标日志** — 区分假设
3. **永远不要"日志一切再 grep"**

**给每条调试日志打标签**，如 `[DEBUG-a4f2]`。清理时一个 grep 搞定。

**性能回归分支**：日志通常是错的。改为：建立基线测量（计时 harness、`performance.now()`、profiler），然后二分。先测量，再修复。

## Phase 5 — 修复 + 回归测试

在有**正确的测试接入点**时，先写回归测试再修复。

正确的接入点 = 测试能执行**真实的 bug 模式**。如果唯一的接入点太浅（单调用者测试但 bug 需要多调用者），回归测试会给出虚假信心。

**如果没有正确的接入点，这本身就是发现。** 记录下来。代码架构阻止了 bug 被锁定。标记给后续处理。

如果有正确接入点：
1. 将最小复现转为失败测试
2. 看它失败
3. 应用修复
4. 看它通过
5. 用 Phase 1 的反馈循环重跑原始场景

## Phase 6 — 清理 + 复盘

完成前必须：
- [ ] 原始复现不再复现（重跑 Phase 1 循环）
- [ ] 回归测试通过（或缺少接入点已记录）
- [ ] 所有 `[DEBUG-...]` 探针已移除
- [ ] 一次性原型已删除
- [ ] 正确的假设写入 commit 信息 — 下一个调试者能学到

**然后问：什么能防止这个 bug 再次发生？** 如果答案涉及架构变更，记录建议。

## 与 tester Agent 的区别

| | tester Agent | diagnose Skill |
|---|---|---|
| 触发 | 编排流程自动 | 用户主动触发 |
| 关注 | AC 通过 + 代码质量 | 根因分析 + 回归测试 |
| 修复 | resume dev 修 | 构建反馈循环 → 假设 → 验证 |
| 场景 | 常规验证 | 顽固 bug、性能问题 |
