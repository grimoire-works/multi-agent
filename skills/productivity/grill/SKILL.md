# Grill — 诘问式对话

对用户的计划、设计或方案进行系统性质疑，逐个问题追问直到消除所有模糊性。

## 核心原则

1. **逐个提问** — 一次只问一个问题，等用户回答后再继续
2. **给推荐答案** — 每个问题附带你的推荐选项，不让用户从零思考
3. **读代码代替猜测** — 能通过读代码回答的问题，先读代码再问
4. **找矛盾** — 用户说的和代码不一致时，立即指出
5. **不急着出方案** — 先把所有问题问完，再给结论

## 工作流程

### 1. 确认诘问目标

明确用户要诘问的对象：
- 设计稿（`doc/design/`）
- 技术方案（`doc/dev/dev-plan.md`）
- PRD（`doc/prd/prd.md`）
- 用户口头描述的计划
- 任意一段代码的设计思路

### 2. 建立问题树

根据目标列出需要确认的维度，形成问题树：

**设计稿诘问**：
- 交互完整性：每个操作都有反馈吗？异常状态怎么展示？
- 边界场景：空数据？超长文本？网络断开？
- 状态流转：页面间数据怎么传递？返回时状态保持吗？
- 响应式：不同屏幕尺寸怎么适配？

**技术方案诘问**：
- 技术选型：为什么选 A 不选 B？有替代方案吗？
- 影响范围：改动会影响已有功能吗？回归测试范围多大？
- 性能：数据量大时还能撑住吗？有瓶颈吗？
- 扩展性：后续需求变化时好改吗？

**PRD 诘问**：
- 用户故事完整性：覆盖了所有用户类型吗？
- 优先级：哪些是必须的？哪些可以后续迭代？
- 数据定义：关键字段的类型、范围、默认值是什么？
- 异常流程：用户操作中断怎么办？数据不一致怎么办？

### 3. 逐个追问

按问题树逐个提问，每个问题的格式：

```
**问题 {N}：{问题标题}**

{具体问题描述}

推荐答案：
- A: {选项A}（推荐）
- B: {选项B}
- C: {选项C}
```

### 4. 记录确认结果

每轮追问后，整理"已确认清单"：

```markdown
## 已确认
| # | 问题 | 结论 |
|---|------|------|
| 1 | {问题} | {用户选择的答案} |

## 待确认
- {下一个问题}
```

### 5. 输出结论

所有问题确认完毕后，输出最终结论：

```markdown
## 诘问完成

### 已确认 {N} 项
{表格}

### 发现的风险
- {风险1}
- {风险2}

### 建议
- {建议1}
- {建议2}
```

## 与 PM 追问的区别

| | PM 追问 | Grill |
|---|---|---|
| 触发时机 | 需求讨论阶段 | 任意阶段 |
| 关注点 | 需求的边界条件 | 方案的完整性和可行性 |
| 使用者 | PM Agent 自动触发 | 用户主动触发 |
| 场景 | 用户提新需求时 | 评审设计稿/技术方案/PRD 时 |
