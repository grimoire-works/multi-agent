# Prompt 编写指南 — Harness 维护者参考

> 本文件是给 **multi-agent-kit 维护者**（包括我未来自己）看的元指南，约束**如何写好 agent prompt / 模板**。
>
> ❌ **不进入 agent prompt**：agent 不需要知道这些原则，它们约束的是**人**，不是 agent。
>
> ✅ 当你修改 `templates/*.md` 或 `src/core/prompt-loader.ts` 时，先读一遍这份指南。

---

## 元原则 1：描述正面设计，不解释反面

### 规则

Prompt 应该只回答「**现在该怎么做**」。不要解释「**为什么不用别的方式**」。

### 为什么

agent 第一次读 prompt 时，没有历史包袱。强行加「不用 X」「Claude Code 不支持 Y」这类反例说明，等于主动把混淆引入 agent 的认知：

- ❌ 「这里有个东西叫 resume，你不能用」← agent：我从来没想过要用啊？
- ❌ 「不用 UUID，用 name」← agent：我并没看到 UUID 概念，你提它干嘛？
- ✅ 「用 name 字符串引用 teammate」← agent 直接照做

### 判断口诀

> 自检：这句话是在描述**现在的设计**，还是在解释**为什么不用别的设计**？后者是噪声，删。

### 例外（可以保留反面说明的场景）

只有当**那种方式是 agent 的常见误解**（基于 LLM 的训练分布，agent 大概率会犯错）时，反面说明才有价值：

- ✅ 「不要用 `git add .`，只 add 实际修改的文件」（agent 常默认 `git add .`）
- ✅ 「不要 mock 数据库，集成测试必须连真实 DB」（agent 常默认 mock）
- ❌ 「不要用 resume」（agent 没听说过 resume）

如果某反面说明只是因为**历史踩过坑**（agent 不会主动犯错），删干净。历史包袱留在 git log / commit message 里。

## 元原则 2：描述职责，不描述实现细节

### 规则

Agent 定义（`.claude/agents/*.md`）管「**怎么干活**」，调用 prompt 只说「**干什么活**」。两层职责分离。

### 为什么

实现细节写在定义里可以复用，写在调用 prompt 里每次重复 + 不一致风险。

### 反例 vs 正例

```
❌ 调用 prompt 写：「请用 Edit 工具追加，不要用 Write，先 Read 文件末尾，再 Edit old_string=最后一行...」
✅ agent 定义里写明这些规则，调用 prompt 只说：「修复 task 15，报告在 doc/test-reports/task-15.md」
```

### 例外

调用方需要**临时覆盖**默认行为时可以重复（如「这次不要写 lessons-learned，因为只是 hotfix」）。

## 元原则 3：约束写硬，建议写软

### 规则

**硬约束**（违反必然出问题）用「必须 / 禁止」；**软建议**（违反不一定出问题但风险高）用「建议 / 优先」。

### 为什么

如果所有规则都用「必须」，agent 无法区分关键性和次要性，遇到冲突时无法取舍。

### 反例 vs 正例

```
❌ 「必须先 Read 文件再 Edit」「必须用 Edit 不用 Write」「必须保持代码风格一致」
   → 三条都用"必须"，agent 无法判断哪个最重要

✅ 「必须用 Edit 追加，禁止 Write 覆盖」「建议保持代码风格一致」「优先复用现有工具函数」
   → 硬约束（不破坏数据）和软建议（提升质量）分得清
```

### 判断标准

> 问：违反这条会**数据丢失 / 流程崩溃**吗？是 → 必须。否 → 建议。

## 元原则 4：通用，不绑定技术栈

### 规则

multi-agent-kit 是**通用 harness**，prompt 不应该假设 Web / 后端 / 移动端 / 特定语言。

### 为什么

假设性例子会让 agent 误以为只能用于那种场景，或在不匹配时强套模板。

### 反例 vs 正例

```
❌ 「拆分维度：建表 / 改字段 / 加路由 / 加鉴权」（全是后端概念）
❌ 「AC 示例：POST /api/register 合法参数 → 返回 201」（只覆盖 Web API）
✅ 「拆分维度：新增模块 / 修改数据结构 / 修改对外接口 / 修改业务流程」（语言无关）
✅ 「AC 示例按项目类型选合适的」（CLI / 库 / 服务 / UI / 数据 多种）
```

### 例外

**领域知识**（具体可执行的检查规则）可以保留，因为不匹配时 agent 会自动跳过：

- ✅ 「ESM 项目中用 require() 会运行时崩溃」（JS 项目适用，其他项目跳过）
- ✅ 「语言探测规则：.dart→Dart, .ts→TypeScript」（必须列具体）

但**举例**（不是规则，只是示例）必须通用化。

## 元原则 5：删冗余，prompt 越短越好

### 规则

每个段落、每个规则都问：「删了 agent 会犯错吗？」。如果不会，删掉。

### 为什么

Token 成本 + 注意力分散。长 prompt 让关键规则被淹没。

### 自检问题

- 这段话 agent 已经从训练数据学到了吗？（如「不要提交密码到 git」对 GPT-4/Claude 是常识，可省）
- 这段话和别的段落重复吗？
- 这段话是给「人」看的（如设计哲学解释）还是给「agent」看的？前者移到本指南。

## 修订 checklist

修改 `templates/*.md` 或 `src/core/prompt-loader.ts` 时，逐条检查：

- [ ] 我加的内容描述的是**怎么做**，不是**为什么不那样做**？（除非是常见误解）
- [ ] 我加的是 agent 行为规则（进 prompt），还是 harness 编写规范（进本指南）？
- [ ] 我的例子是通用的，还是绑定到某个技术栈？
- [ ] 硬约束（必须 / 禁止）和软建议（建议 / 优先）区分清楚了吗？
- [ ] 删了这条 agent 会犯错吗？不会就删。

## 配套：原则间关系

| 原则 | 与本指南其他原则的关系 |
|------|----------------------|
| 元原则 1（正面设计） | 优先级最高，违反这条 = 引入认知污染 |
| 元原则 2（职责分离） | 配合「定义管怎么干，prompt 管干什么」的项目架构 |
| 元原则 3（硬软区分） | 让 agent 在冲突时能取舍 |
| 元原则 4（通用化） | 多-agent-kit 的核心定位，违反 = 失去通用性 |
| 元原则 5（删冗余） | 与 1-4 配合，做收尾精简 |

冲突时按以下顺序决策：

```
元原则 1（正面） > 元原则 4（通用） > 元原则 2（职责分离） > 元原则 3（硬软区分） > 元原则 5（精简）
```

例：「这个反面说明是历史包袱（违反元原则 1），但能帮 agent 避免常见误解」→ 元原则 1 优先，但保留反面说明可接受（这就是元原则 1 的"例外"场景）。
