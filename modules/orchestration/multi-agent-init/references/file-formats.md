# 文件格式定义

初始化时需要生成的各类文件格式规范。Skill 执行到 Step 5 时按此格式创建文件。

## .claude/settings.local.json

```json
{
  "permissions": {
    "allow": [
      "Bash({构建命令}:*)",
      "Bash({测试命令}:*)",
      "Bash({依赖安装命令}:*)",
      "Bash(find ~/.claude/projects/:*)",
      "Bash(mkdir -p:*)"
    ]
  }
}
```

## .claude/rules/principles.md

**直接拷贝 `references/principles.md` 的完整内容**到目标项目。本文件定义通用协作原则（P-001 ~ P-006），与具体技术栈无关。

**理由**：所有项目都需要这套协作 meta-rule（何时询问 / 改动前先定位 / 同类根因升级 / 状态机完整性 / 共享资源同步 / 完整链路验证）。项目特定的业务规则不写进此文件，由用户后续手动维护到 `.claude/rules/project-specific.md`。

**增量模式**：如果文件已存在，**不覆盖**（用户可能已调整）。仅在文件不存在时拷贝。

## doc/plan.md

**初始化时只生成空模板（仅含 Task 0 环境验证），不自动填充任务。** 具体开发任务由用户提供需求后，通过编排流程委托 PM Agent（`{代号}-pm`）分析拆解生成，或由用户手动填写。

**原因**：初始化阶段不应假设用户要做什么功能，任务规划应在用户明确需求后才进行。

空模板格式：

```markdown
# 开发计划 — {项目名称}

## 项目概述
{一句话描述}

## 任务列表
| # | 任务 | 状态 | 涉及文件 | 验收标准 | 备注 |
|---|------|------|----------|----------|------|
| 0 | 环境验证 + 编译检查 | ⏳ 待办 | - | 构建命令零错误 | 主Agent直接做 |

## 当前进度
- 正在执行：尚未开始
- 已完成：0/0
```

任务填写规范（供 PM Agent 或用户手动填写时参考）：
- **粒度细**：每个任务 30-150 行代码量（宁可多拆，不要堆大）
- **AC 上限**：每任务 1-3 条 AC，**最多 3 条**。超过 3 条必须按 AC 边界拆分为多个任务
- **文件数上限**：单任务涉及文件 ≤ 3 个；同一文件的多次改造应拆为串行的多个任务（避免合并冲突，便于并行）
- 每条 AC 格式为"操作 → 期望结果"，必须可执行可验证。示例（按项目类型选合适的）：
  - CLI 工具：`运行 xxx --input fixture.json → 输出包含 "success" 且 exit code 0`
  - 库/模块：`调用 X() 入参 Y → 返回非空列表且元素 ≥ 1`
  - 服务/API：`POST /xxx 合法参数 → 返回 2xx 且响应体含 xxx 字段`
  - UI 类：`点击按钮 X → 元素 Y 出现且文本 = "..."`（可选：截图对比）
  - 数据处理：`输入 fixture.csv → 输出行数 = N 且第一行字段 = "..."`
- "涉及文件"列必须填写，用于 Wave 分组时的文件冲突检测。格式为逗号分隔的文件路径（如 `src/core/parser.py, src/core/models/note.py`）
- "验收标准"列填写"见 AC-N"并在下方 AC 段落中定义具体标准
- **拆分反模式**（必须避免）：
  - ❌ "Task N：X 功能的配套改造"（多个无关子改造塞一起）→ 按子改造拆分
  - ❌ "Task N：底层重构 + 业务适配 + 兼容处理"（多技术变更混合）→ 按变更类型拆
  - ❌ "Task N：完整 X 功能"（横跨 UI/接口/数据/测试多层）→ 按层次拆
  - ❌ 单任务涉及 5+ 文件
  - ✅ 拆分维度：按**层次** / 按**子能力** / 按**技术变更类型**
  - ✅ 一个任务只在一个层次或一种技术变更上做事

## doc/lessons-learned.md

空文件，只写标题：`# 经验教训库`

### 结构化经验格式（v2）

每条经验使用以下格式写入：

```markdown
### EXP-{NNN}: {简短标题}

| 字段 | 值 |
|------|-----|
| 日期 | {mmdd} |
| 触发条件 | {什么场景下会遇到} |
| 域 | {从下方域标签中选 1-2 个} |
| 置信度 | 0.3 |
| 命中次数 | 0 |
| 最后命中 | {mmdd} |
| 来源 | {agent-type}:{task-id} |
| 类型 | bug-fix / prompt-feedback / best-practice / anti-pattern |

**原因**：{为什么会出这个问题}

**解法**：{怎么解决的}
```

### 字段定义

**域标签分类**（agent 写入时从中选择 1-2 个）：
- `backend` — 后端逻辑、API、数据库
- `frontend` — 前端组件、页面、路由
- `testing` — 测试策略、AC 验证
- `architecture` — 架构设计、模块划分
- `performance` — 性能优化、资源管理
- `ui` — UI 样式、布局、动画
- `security` — 安全漏洞、权限控制
- `prompt` — 提示词优化、Agent 指令
- `tooling` — 构建工具、CI/CD、环境配置

**类型分类**：
- `bug-fix` — 修复 bug 后总结的经验
- `prompt-feedback` — prompt 描述不够清晰导致的修正（≥2 轮修正时使用）
- `best-practice` — 开发过程中发现的最佳实践
- `anti-pattern` — 发现的反模式，需要避免

**置信度晋升规则**：
- 0.3 → 新建（默认）
- 0.5 → 命中 1-2 次（由 `/learn` 从 main-log.md 统计注入次数）或来自 diagnose 产出
- 0.7 → 命中 3+ 次
- 0.9 → 已提升为项目规则

**置信度衰减规则**（由 `/learn` 自动执行）：
- `最后命中` 距当前日期 ≥ 30 天 → 置信度 -0.1
- 置信度降到 0.1 以下 → 标记为归档候选

**最后命中字段维护**：
- 新建时：`最后命中` = 创建日期（即与 `日期` 字段相同）
- `/learn` 运行时：从 main-log.md 统计命中次数后，同步更新 `最后命中` 为日志中最后一次注入的日期

### 经验生命周期

```
新建（0.3）→ 被注入命中 → 置信度上升 → 提升为规则（0.9）
                 ↓
           长期未命中 → 置信度衰减 → 归档（移到 archive 文件）
```

### 归档标准（三个条件必须同时满足）

| 条件 | 阈值 | 说明 |
|------|------|------|
| 距上次命中 | ≥ 30 天 | 长时间没人触发 |
| 置信度 | ≤ 0.3 | 从未真正验证 |
| 命中次数 | ≤ 1 | 只被注入过一次 |

### 旧格式（兼容）

```markdown
- [mmdd] 经验描述
  - 原因：为什么会出这个问题
  - 解法：怎么解决的
```

旧格式条目仍然有效，编排器注入时同时匹配新旧格式。`/learn` skill 可建议将旧格式升级为新格式。

## doc/lessons-archive.md

归档经验存储文件。初始化时不创建，由 `/learn` skill 在归档时自动创建。

格式：`# 经验教训归档`

归档条目保持原格式，末尾追加归档信息：

```markdown
### EXP-{NNN}: {标题}

| 字段 | 值 |
|------|-----|
| ... | ...（原有字段不变） |
| 归档日期 | {mmdd} |
| 归档原因 | {衰减/合并/用户手动} |
```

- Agent 和编排器**不读取**此文件
- `/learn` skill **可读取**此文件，用于恢复和跨周期分析
- 归档不是删除，条目可被恢复回活跃文件
