# 通用协作原则 — Multi-Agent Harness

> 本文件是 multi-agent-kit 的默认规则池。`/multi-agent-init` 时拷贝到目标项目的 `.claude/rules/principles.md`，作为 orchestrator / dev / tester 三类 agent 共同遵守的 meta-rule。
>
> 这些原则**与具体技术栈无关**（不绑定 Web / 后端 / 移动端 / 数据库 / 语言），只约束 agent 的**决策方式、协作方式、验证方式**。

---

## 责任分布

| 原则 | 主智能体 | 开发 Agent | 测试 Agent |
|------|:------:|:--------:|:--------:|
| P-001 不询问门槛 | ✅ | — | — |
| P-002 改动前先定位 | ✅ | — | — |
| P-003 同类根因升级 | ✅ | ✅（写入） | ✅（写入） |
| P-004 状态机完整性 | — | ✅ | ✅（验证） |
| P-005 共享资源同步 | — | ✅ | ✅（验证） |
| P-006 完整链路验证 | — | — | ✅ |
| P-007 参考实现系统化对照 | ✅ | ✅ | ✅（验证） |
| P-008 PRD 降级保留已上线功能 | ✅（决策） | — | ✅（验证） |

## P-001：AskUserQuestion 门槛

**适用角色**：主智能体

### 规则

只在「**多种合理设计选项需要用户决策**」时使用 AskUserQuestion。

### 禁止场景（直接执行，不询问）

1. 修复方向只有一种合理选项（踩坑后补缺失规则 / 修拼写 / 补缺失字段）
2. 用户已表达过偏好，同类设计直接套用
3. 经验库（lessons-learned）已有明确解法的同类问题
4. 同一根因已踩过 ≥2 次（按 P-003 升全局修复）

### 判断口诀

> 如果用户回答只可能是「是，做」或「随你」，那就**别问**。

### 应当询问的场景

1. 多种合理设计选项有不同 trade-off，需要用户判断优先级
2. 业务规则不明确，存在多种合理解读
3. 改动会破坏向后兼容，需要用户确认影响范围
4. 涉及外部系统 / 第三方选型

### 反例 vs 正例

```
❌ "要不要把 [hidden] bug 升全局规则？"  → 显然该做，别问
✅ "状态恢复选 A（客户端补发）还是 B（服务端异步）？"  → 真有 trade-off，问
```

## P-002：改动前先定位

**适用角色**：主智能体

### 规则

委托 dev / frontend agent 改动任何对象前，主 Agent 必须**先用搜索工具定位目标实际位置**（文件 + 行号），在委托 prompt 中给出具体 `file:line`。

### 禁止行为

- ❌ 靠用户口语描述定位（用户说「首页登录」可能指主页 modal，也可能指独立 login 页）
- ❌ 靠凭印象、凭上次会话记忆定位（代码可能已变化）
- ❌ 让 dev 自己猜目标位置

### 必做步骤

```
1. 用 Grep / Glob 找目标元素（className / id / 函数名 / 路由名 / 文件名）
2. 确认是否有多处匹配
3. 委托 prompt 中给出 file:line
```

### 反例 vs 正例

```
❌ "用户反馈首页登录按钮太丑，请改一下"  → dev 不知道是 index.html 还是 login.html
✅ "用户反馈首页登录按钮太丑，目标在 src/pages/index.html:42 的 .login-btn，
    请按 doc/design/xxx.md 重设计"  → dev 直接动手
```

## P-003：同类根因升级机制

**适用角色**：主智能体（决策）+ dev/tester（写入）

### 规则

同一**根因**（不分语言 / 技术栈 / 表面现象）出现 ≥2 次 → 主 Agent 必须主动升级处理等级。

### 升级阶梯

| 阶段 | 触发 | 必做动作 |
|------|------|---------|
| L1 | 第 1 次踩 | dev/tester 写入 lessons-learned，置信度 0.3-0.5 |
| L2 | 第 2 次踩 | 主 Agent 提升置信度到 ≥0.8 + 写「升规则建议」到 `.claude/rules/` |
| L3 | 第 3 次踩（应不再发生） | 主 Agent 失职；写 postmortem 分析为何 L2 没拦住 |

### 「同一根因」判定

不看表面现象，看底层原因：
- ✅ 同一根因：「显式声明覆盖原生隐式行为」「多阶段流程只建模终态」
- ❌ 不同根因：「用户登录失败」 vs 「邀请码无效」（表面相似但根因不同）

### 禁止

- ❌ 第 3 次踩时仍只做**局部补丁**（如只修当前组件，不写全局兜底）
- ❌ 口头总结而不入库（无法被 `/learn` 扫描）

## P-004：状态机 / 多阶段流程完整性

**适用角色**：dev（实现）+ tester（验证）

### 规则

涉及**多阶段流程**（API 拆分 / 状态机 / 生命周期 / 断点续跑 / 异步任务 / 轮询）时，dev 必须在动手前显式产出状态模型。

### 必须产出

```
1. 状态枚举：S0（初始）→ S1 → S2 → ... → 终态 / 失败态
   （不允许只建模「初始 / 终态」二态）

2. 转换条件：每个 S(n) → S(n+1) 的触发条件、副作用、可见反馈

3. 中断点分析：每个状态可能被什么打断？
   - 用户主动中断（关闭 / 刷新 / 取消）
   - 网络中断
   - 服务重启
   - TTL 过期
   - 并发触发

4. 恢复策略：每个中断点的处理方式
   - 能否恢复？需要什么上下文？
   - 不能恢复时如何降级（清状态 / 提示用户 / 自动重试）
```

### 自检清单（每个状态问一遍）

- [ ] 用户在这个状态下**关掉重开**，会发生什么？
- [ ] 用户在这个状态下**断网 30 秒**，会发生什么？
- [ ] **服务重启**后这个状态还在吗？
- [ ] 同一用户**并发触发**两次会怎样？

### 文档要求

状态模型必须体现在以下任一位置：
- 代码注释（核心状态机顶部）
- 技术方案文档（`doc/dev/dev-plan.md`）
- API 文档（涉及 API 时）

**不允许只在脑子里建模**。

### 反例 vs 正例

```
❌ 两段式 API：status 只有 running / done  → 中途刷新永远卡 running
✅ 两段式 API：status 有 running / stage_1_done / done / failed  → 中间状态可恢复
```

## P-005：共享资源变更同步

**适用角色**：dev（实施）+ tester（验证）

### 规则

修改任何**被多处引用**的资源时，dev 必须同步更新所有引用点；tester 必须验证是否全部同步。

### 共享资源类型（非穷举）

| 资源类型 | 同步项 |
|---------|--------|
| 静态文件（CSS / JS / 图片 / 字体） | 所有引用方的 cache-busting 版本号 / hash |
| API 接口签名（path / method / params / response） | 所有调用方（前端 / SDK / 文档 / mock） |
| DB schema（表结构 / 字段 / 索引） | ORM 模型 / DTO / migration 脚本 / 数据字典 |
| 环境变量改名 / 增删 | `.env.example` + 所有读取代码 + 部署文档 |
| 公共函数签名（参数 / 返回值 / 异常） | 所有调用点的传参 / 类型定义 |
| 配置 schema（JSON / YAML / TOML） | 所有消费方的兼容性 / fallback |
| 共享类型定义（Protocol / Interface） | 所有 implementor / consumer |

### 必做步骤

```
1. 改动前 Grep / Glob 找到所有引用点
2. 列出引用清单（数量 + 路径）
3. 改动后逐个确认已同步
4. 自检：grep 老的引用方式，应无结果
```

### 禁止

- ❌ 只改当前直接修改的文件，不查其他引用
- ❌ 改了接口签名但忘了改 mock / 文档
- ❌ 改了 DB 字段但 ORM 模型未同步
- ❌ 改了静态文件但 cache-busting token 未 bump

### 反例 vs 正例

```
❌ 改了 style.css，只 bump 当前页面的 ?v=123  → 其他 5 个页面仍用旧 ?v=122
✅ 改了 style.css，grep 找到所有引用的 HTML（6 个），同步 bump 到 ?v=124
```

## P-006：完整链路验证

**适用角色**：tester

### 规则

测试改动时必须覆盖**「触发 → 处理 → 输出」完整链路**，不能只测中间某一层就 PASS。

### 各类改动的完整链路

| 改动类型 | 完整链路（必须覆盖） | 不允许的「单层通过」 |
|---------|-------------------|-------------------|
| 前端 UI | DOM 事件 → 网络请求 → 渲染结果 | 仅 curl API 返回 200 |
| 后端 API | HTTP → 业务逻辑 → DB / 副作用 | 仅函数单测通过 |
| DB schema | 迁移脚本 → 数据正确性 → 老数据兼容 | 仅 migration 不报错 |
| 状态机 | 正常路径 + 每个中间状态的中断恢复 | 仅 happy path |
| 鉴权 / 权限 | 正常用户 + 越权 + 过期 + 无 token | 仅正常用户通过 |
| 异步任务 | 提交 → 队列 → 执行 → 结果可查 | 仅提交接口返回 200 |
| 缓存 | 写入 → 读取 → 失效 → 兜底 | 仅写入成功 |

### 测试报告必须显式声明

```
✅ "已实测完整链路：DOM 点击 → POST /api/x → DB 写入 → 渲染更新"
⚠️ "未覆盖 xxx 层（如浏览器渲染），建议人工验证"
```

**不允许**：silent skip 关键验证 + 直接 PASS。

### 自检问题（测试结束前问自己）

- [ ] 我测的是**端到端**还是**单元**？
- [ ] 如果整个链路中某一环坏了，我的测试能发现吗？
- [ ] 我有没有「依赖构建通过 / 静态分析通过」就给 PASS？（不能）

### 反例 vs 正例

```
❌ 前端 JS 改动：curl API 通过 → PASS  → 用户浏览器实际加载了旧 JS（缓存）
✅ 前端 JS 改动：headless 浏览器或人工验证 DOM 事件链路 + 检查 HTML 中所有 <script> 都带版本 token
```

## 原则间优先级

冲突时按以下顺序决策（左服从右）：

```
P-001（不问） < P-002（先定位） < P-003（升规则） < P-006（完整验证） < P-004（状态机） < P-005（资源同步） < P-007（参考对照） < P-008（PRD 保留已上线功能）
```

**例**：用户催着发布（P-001 不问），但改动涉及共享接口（P-005）→ 仍必须 grep 所有调用点同步，不能跳过。

**例**：用户说「这个页面跟老版本对齐一下就行」（P-001 不问 + P-007 参考对照）→ 仍必须按 P-007 系统化对照流程，不能凭印象改两处就交差。

**例**：PM Agent 在 PRD 中建议「30 天学习计划 W2 再做」（P-001 不问 + P-008 PRD 保留）→ 仍必须按 P-008 检查「老前端是否已上线」，已上线核心功能禁止降级。

## P-007：参考实现系统化对照

**适用角色**：主智能体（决策）+ dev（执行）+ tester（验证）

### 规则

任何「**以现有系统为参考做新实现**」的任务，必须按系统化对照流程，禁止碎片化响应或靠印象填值。

### 适用场景（非穷举）

| 场景 | 参考实现 | 对照维度 |
|------|---------|---------|
| 老前端 → 新框架迁移（如 vanilla JS → Vue/React） | 老 HTML + CSS + JS | DOM + 样式 + 文案 + 交互 |
| 老后端 → 新语言 / 框架重写 | 老 API + DB schema + 中间件 | 接口签名 + 字段 + 错误码 + 鉴权 |
| 设计稿 → 实现 | Figma / Sketch / 截图 | 视觉 token + 间距 + 字号 + 配色 |
| 竞品功能复刻 | 竞品 UI / API | 功能 + 交互 + 数据结构 |
| 协议适配（OAuth / SAML / 自定义） | 协议规范文档 | 字段语义 + 边界 + 错误处理 |
| DB 迁移（如 MySQL → PostgreSQL） | 老 schema + 数据字典 | 表结构 + 类型映射 + 约束 + 触发器 |

### 必做步骤

```
1. 列清单：Glob 老项目所有相关源文件（HTML / 模板 / 配置 / API 定义），
   建立「参考实现 → 新实现」映射表

2. grep 全资源目录：每个 class / 函数 / 标识符 / 配置项都 grep 全目录找定义位置
   （不假设在哪个文件，跨文件依赖很常见，如 .error 定义在 app.css 而非 login.css）

3. 逐属性对照表：每个选择器 / 函数签名 / 配置项列真实值
   （100% 从源文件复制，不靠印象），写入 doc/diff-XXX.md

4. 三层对齐：
   - 结构层：DOM / 函数签名 / 接口路径
   - 文案层：placeholder / 标题 / 按钮文字 / 日志 / 错误提示
   - 行为层：状态机 / loading 态 / 错误处理 / 跳转 / redirect / 鉴权

5. 兼容老路径：参考实现暴露的 URL / API 路径 / 命令行参数 / 配置 key
   用户可能依赖，必须加重定向 / 别名 / 兼容层

6. 运行时数据兜底：依赖外部数据（API / 配置中心）时必须加 fallback 常量，
   dev 阶段外部不可用也能完整渲染（不能纯依赖 API）

7. 代码层 0 差异目标：提交时禁止说「请浏览器自测」「请用户手动复核」，
   要么代码层 0 差异自证（diff 对照表 + 自检全过），
   要么明确列出剩余差异让用户定夺
```

### 禁止行为

- ❌ 靠印象填 CSS / 配置值（如「印象中」padding 16 实际 32、字重 700 实际 600、圆角 8 实际 12）
- ❌ 只读相邻文件不 grep（跨文件依赖如 `.error` 定义在 `app.css:200` 而非 `login.css`）
- ❌ 碎片化响应（用户指出一处改一处，不主动系统遍历所有参考文件）
- ❌ 把 QA 责任甩给用户（提交时说「请浏览器自测」「请人工复核」）
- ❌ 假设外部 API 永远成功（dev 阶段后端没起时全部字段显示「—」占位符）
- ❌ 假设 UI 库默认值 = 老前端定制值（如 Element Plus primary 绿色 ≠ 老前端管理员登录的紫色主题）

### 反例 vs 正例

```
❌ 用户反馈「样式不对」
   → 看相邻 CSS 文件
   → 凭印象填值
   → 提交说「请浏览器自测」
   → 用户再反馈另一处不对 → 循环 7 次

✅ 用户反馈「样式不对」
   → Glob 老项目所有 HTML
   → grep 全 CSS 目录找类定义
   → 写对照表到 doc/diff-XXX.md
   → 修复
   → 自检代码层 0 差异
   → 提交附完整对照表，不再让用户当 QA
```

### 自检问题（提交前必问）

- [ ] 我读完了参考实现的**完整文件**（不只前 100 行）？
- [ ] 我 grep 了所有相关 CSS / 配置 / 函数定义（不假设文件位置）？
- [ ] 每个 CSS 值 / 配置项都从源文件直接复制（不是凭印象）？
- [ ] 结构层 + 文案层 + 行为层三层都对齐了？
- [ ] 参考实现暴露的路径 / API / 参数有重定向或兼容层吗？
- [ ] 外部依赖有 fallback 兜底吗？
- [ ] 我有没有说「请浏览器自测」「请人工复核」？（如果有，本次提交不合格）

### 与其他原则的关系

P-007 是 P-002（先定位）+ P-005（资源同步）+ P-006（完整验证）在「参考实现对照」场景下的**特化与强化**：

- P-002 关注「定位修改目标」（本项目的当前代码）
- P-005 关注「同步本项目引用点」（修改共享资源时同步所有调用方）
- P-006 关注「端到端验证」（触发 → 处理 → 输出）
- **P-007 关注「与外部参考实现对齐」**——这是上面三者都不专门覆盖的场景

### 升规则触发

参考实现对照在项目中**反复被违反**（≥3 次）→ 应升级为项目专属规则，写入 `.claude/rules/project-specific.md`，列出该项目特有的参考实现路径与对照维度。

## P-008：PRD 降级决策保留老前端已上线功能

**适用角色**：主智能体（决策）+ PM Agent（写 PRD）+ tester（验证）

### 规则

PRD 做「降级 / 推迟 / 占位 disabled」决策时，**必须区分**「老前端已上线功能」vs「新增功能」。已上线核心功能**禁止降级**，必须迁移。

### 判定流程（必走）

```
1. 这个功能在参考实现（老前端 / 老后端 / 上一版本）是否已上线？
   - 是 → 进入步骤 2
   - 否 → 进入步骤 4

2. 是核心功能还是边缘增强？
   - 核心（影响主流程 / 用户高频使用 / 无等价替代）→ 禁止降级，必须迁移
   - 边缘（增强 / 装饰 / 可跳过）→ 进入步骤 3

3. 即使边缘增强，降级时也要明确标注「参考实现有，新版本暂缓，X 期内补回」，
   不能等同于「不实现」

4. 新增功能 → 按 P-001 ~ P-007 正常决策优先级
```

### 禁止行为

- ❌ PRD 降级决策只看「工时估算」，不看「是否已上线」
- ❌ 把「下线已上线功能」与「推迟增强功能」混为一谈
- ❌ 用「占位 disabled」按钮代替真实功能迁移（用户看到的就是「功能没了」）
- ❌ PRD 不附「老前端已上线功能清单」就直接做降级决策

### 反例 vs 正例

```
❌ PRD §9 降级清单：
   - onboarding 引导（增强）       ← 可降级
   - compare 比较（增强）           ← 可降级
   - 雷达图（可视化增强）           ← 可降级
   - 30 天学习计划（核心已上线）    ← ❌ 不应降级！老前端用户每天都在用
   - markdown 渲染（核心已上线）    ← ❌ 不应降级！老前端已有 .md 全局样式
   - task-polling 恢复（核心）      ← ❌ 不应降级！老前端已实现 requirements_done 自动补 stage2

✅ PRD §9 降级清单（正确分层）：
   核心已上线功能（禁止降级，必须迁移）：
     - 30 天学习计划 / markdown 渲染 / task-polling 完整恢复 / ...
   边缘增强（可降级，明确标注补回时间）：
     - onboarding 引导（W2 补）
     - compare 比较（W2 补）
     - 雷达图（W2 补）
   新增功能（按业务优先级排）：
     - ...
```

### 必做步骤

1. **建立「老前端已上线功能清单」**：列每个功能 + 模块大小 + 用户使用频率 + 后端 API 是否就绪
2. **核心 vs 边缘分类**：影响主流程的 = 核心
3. **PRD 决策表三档**：
   - 核心已上线 → **禁止降级**，排入当前 sprint
   - 边缘增强 → 可降级，标注「X 期补回」
   - 新增 → 正常排优先级
4. **PM Agent 写完 PRD 后，主 Agent 必须二次审核**：grep PRD 中所有「W2 deferred」「占位 disabled」「不实现」关键词，逐项对照「老前端已上线功能清单」

### 自检问题（PRD 完成前必问）

- [ ] 我列了老前端所有已上线功能吗？
- [ ] PRD 中每个「降级」决策，对应的「老前端是否已上线」我查了吗？
- [ ] 用户切到新版本后，会不会发现「原本能用的功能没了」？
- [ ] 降级清单是否分了「核心 / 边缘 / 新增」三档？

### 与其他原则的关系

P-008 是 P-003（同类根因升级）在 **PRD 决策层**的特化：
- P-003 关注「代码层同类根因」
- P-008 关注「PRD 层同类根因」——决策错误比代码错误影响更大（一批功能被错误下线）

### 升规则触发

某项目 PRD 反复出现「已上线功能被降级」（≥1 次）→ 应升级为项目专属规则，写入 `.claude/rules/project-specific.md`，列该项目老前端已上线功能清单。

某条原则在项目中**反复被违反**（≥3 次）→ 应升级为项目专属规则，写入 `.claude/rules/project-specific.md`，作为编排时必注入的强约束。


## 与项目特定规则的关系

本文件**只放通用原则**（跨项目可复用）。

项目特定的业务规则（如「本项目用 Tailwind 不用 emotion」「本项目 DB 必须用 migration 工具」）写到 `.claude/rules/project-specific.md`，不要写进本文件。

主智能体编排时，两类规则一起注入 dev/tester agent prompt：

```
必须遵守的项目规则：
1. 通用原则（.claude/rules/principles.md）
2. 项目专属规则（.claude/rules/project-specific.md）
```
