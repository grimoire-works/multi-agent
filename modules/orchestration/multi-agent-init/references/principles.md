# 通用协作原则 — Multi-Agent Harness

> 本文件是 multi-agent-kit 的默认规则池。`/multi-agent-init` 时拷贝到目标项目的 `.claude/rules/principles.md`，作为 orchestrator / dev / tester 三类 agent 共同遵守的 meta-rule。
>
> 这些原则**与具体技术栈无关**（不绑定 Web / 后端 / 移动端 / 数据库 / 语言），只约束 agent 的**决策方式、协作方式、验证方式**。

---

## 责任分布

| 原则 | 主智能体 | 开发 Agent | 测试 Agent |
|------|:------:|:--------:|:--------:|
| P-001 不询问门槛 | ✅ | — | — |
| P-002 改动前先定位 | ✅ | — | — |
| P-003 同类根因升级 | ✅ | ✅（写入） | ✅（写入） |
| P-004 状态机完整性 | — | ✅ | ✅（验证） |
| P-005 共享资源同步 | — | ✅ | ✅（验证） |
| P-006 完整链路验证 | — | — | ✅ |

## P-001：AskUserQuestion 门槛

**适用角色**：主智能体

### 规则

只在「**多种合理设计选项需要用户决策**」时使用 AskUserQuestion。

### 禁止场景（直接执行，不询问）

1. 修复方向只有一种合理选项（踩坑后补缺失规则 / 修拼写 / 补缺失字段）
2. 用户已表达过偏好，同类设计直接套用
3. 经验库（lessons-learned）已有明确解法的同类问题
4. 同一根因已踩过 ≥2 次（按 P-003 升全局修复）

### 判断口诀

> 如果用户回答只可能是「是，做」或「随你」，那就**别问**。

### 应当询问的场景

1. 多种合理设计选项有不同 trade-off，需要用户判断优先级
2. 业务规则不明确，存在多种合理解读
3. 改动会破坏向后兼容，需要用户确认影响范围
4. 涉及外部系统 / 第三方选型

### 反例 vs 正例

```
❌ "要不要把 [hidden] bug 升全局规则？"  → 显然该做，别问
✅ "状态恢复选 A（客户端补发）还是 B（服务端异步）？"  → 真有 trade-off，问
```

## P-002：改动前先定位

**适用角色**：主智能体

### 规则

委托 dev / frontend agent 改动任何对象前，主 Agent 必须**先用搜索工具定位目标实际位置**（文件 + 行号），在委托 prompt 中给出具体 `file:line`。

### 禁止行为

- ❌ 靠用户口语描述定位（用户说「首页登录」可能指主页 modal，也可能指独立 login 页）
- ❌ 靠凭印象、凭上次会话记忆定位（代码可能已变化）
- ❌ 让 dev 自己猜目标位置

### 必做步骤

```
1. 用 Grep / Glob 找目标元素（className / id / 函数名 / 路由名 / 文件名）
2. 确认是否有多处匹配
3. 委托 prompt 中给出 file:line
```

### 反例 vs 正例

```
❌ "用户反馈首页登录按钮太丑，请改一下"  → dev 不知道是 index.html 还是 login.html
✅ "用户反馈首页登录按钮太丑，目标在 src/pages/index.html:42 的 .login-btn，
    请按 doc/design/xxx.md 重设计"  → dev 直接动手
```

## P-003：同类根因升级机制

**适用角色**：主智能体（决策）+ dev/tester（写入）

### 规则

同一**根因**（不分语言 / 技术栈 / 表面现象）出现 ≥2 次 → 主 Agent 必须主动升级处理等级。

### 升级阶梯

| 阶段 | 触发 | 必做动作 |
|------|------|---------|
| L1 | 第 1 次踩 | dev/tester 写入 lessons-learned，置信度 0.3-0.5 |
| L2 | 第 2 次踩 | 主 Agent 提升置信度到 ≥0.8 + 写「升规则建议」到 `.claude/rules/` |
| L3 | 第 3 次踩（应不再发生） | 主 Agent 失职；写 postmortem 分析为何 L2 没拦住 |

### 「同一根因」判定

不看表面现象，看底层原因：
- ✅ 同一根因：「显式声明覆盖原生隐式行为」「多阶段流程只建模终态」
- ❌ 不同根因：「用户登录失败」 vs 「邀请码无效」（表面相似但根因不同）

### 禁止

- ❌ 第 3 次踩时仍只做**局部补丁**（如只修当前组件，不写全局兜底）
- ❌ 口头总结而不入库（无法被 `/learn` 扫描）

## P-004：状态机 / 多阶段流程完整性

**适用角色**：dev（实现）+ tester（验证）

### 规则

涉及**多阶段流程**（API 拆分 / 状态机 / 生命周期 / 断点续跑 / 异步任务 / 轮询）时，dev 必须在动手前显式产出状态模型。

### 必须产出

```
1. 状态枚举：S0（初始）→ S1 → S2 → ... → 终态 / 失败态
   （不允许只建模「初始 / 终态」二态）

2. 转换条件：每个 S(n) → S(n+1) 的触发条件、副作用、可见反馈

3. 中断点分析：每个状态可能被什么打断？
   - 用户主动中断（关闭 / 刷新 / 取消）
   - 网络中断
   - 服务重启
   - TTL 过期
   - 并发触发

4. 恢复策略：每个中断点的处理方式
   - 能否恢复？需要什么上下文？
   - 不能恢复时如何降级（清状态 / 提示用户 / 自动重试）
```

### 自检清单（每个状态问一遍）

- [ ] 用户在这个状态下**关掉重开**，会发生什么？
- [ ] 用户在这个状态下**断网 30 秒**，会发生什么？
- [ ] **服务重启**后这个状态还在吗？
- [ ] 同一用户**并发触发**两次会怎样？

### 文档要求

状态模型必须体现在以下任一位置：
- 代码注释（核心状态机顶部）
- 技术方案文档（`doc/dev/dev-plan.md`）
- API 文档（涉及 API 时）

**不允许只在脑子里建模**。

### 反例 vs 正例

```
❌ 两段式 API：status 只有 running / done  → 中途刷新永远卡 running
✅ 两段式 API：status 有 running / stage_1_done / done / failed  → 中间状态可恢复
```

## P-005：共享资源变更同步

**适用角色**：dev（实施）+ tester（验证）

### 规则

修改任何**被多处引用**的资源时，dev 必须同步更新所有引用点；tester 必须验证是否全部同步。

### 共享资源类型（非穷举）

| 资源类型 | 同步项 |
|---------|--------|
| 静态文件（CSS / JS / 图片 / 字体） | 所有引用方的 cache-busting 版本号 / hash |
| API 接口签名（path / method / params / response） | 所有调用方（前端 / SDK / 文档 / mock） |
| DB schema（表结构 / 字段 / 索引） | ORM 模型 / DTO / migration 脚本 / 数据字典 |
| 环境变量改名 / 增删 | `.env.example` + 所有读取代码 + 部署文档 |
| 公共函数签名（参数 / 返回值 / 异常） | 所有调用点的传参 / 类型定义 |
| 配置 schema（JSON / YAML / TOML） | 所有消费方的兼容性 / fallback |
| 共享类型定义（Protocol / Interface） | 所有 implementor / consumer |

### 必做步骤

```
1. 改动前 Grep / Glob 找到所有引用点
2. 列出引用清单（数量 + 路径）
3. 改动后逐个确认已同步
4. 自检：grep 老的引用方式，应无结果
```

### 禁止

- ❌ 只改当前直接修改的文件，不查其他引用
- ❌ 改了接口签名但忘了改 mock / 文档
- ❌ 改了 DB 字段但 ORM 模型未同步
- ❌ 改了静态文件但 cache-busting token 未 bump

### 反例 vs 正例

```
❌ 改了 style.css，只 bump 当前页面的 ?v=123  → 其他 5 个页面仍用旧 ?v=122
✅ 改了 style.css，grep 找到所有引用的 HTML（6 个），同步 bump 到 ?v=124
```

## P-006：完整链路验证

**适用角色**：tester

### 规则

测试改动时必须覆盖**「触发 → 处理 → 输出」完整链路**，不能只测中间某一层就 PASS。

### 各类改动的完整链路

| 改动类型 | 完整链路（必须覆盖） | 不允许的「单层通过」 |
|---------|-------------------|-------------------|
| 前端 UI | DOM 事件 → 网络请求 → 渲染结果 | 仅 curl API 返回 200 |
| 后端 API | HTTP → 业务逻辑 → DB / 副作用 | 仅函数单测通过 |
| DB schema | 迁移脚本 → 数据正确性 → 老数据兼容 | 仅 migration 不报错 |
| 状态机 | 正常路径 + 每个中间状态的中断恢复 | 仅 happy path |
| 鉴权 / 权限 | 正常用户 + 越权 + 过期 + 无 token | 仅正常用户通过 |
| 异步任务 | 提交 → 队列 → 执行 → 结果可查 | 仅提交接口返回 200 |
| 缓存 | 写入 → 读取 → 失效 → 兜底 | 仅写入成功 |

### 测试报告必须显式声明

```
✅ "已实测完整链路：DOM 点击 → POST /api/x → DB 写入 → 渲染更新"
⚠️ "未覆盖 xxx 层（如浏览器渲染），建议人工验证"
```

**不允许**：silent skip 关键验证 + 直接 PASS。

### 自检问题（测试结束前问自己）

- [ ] 我测的是**端到端**还是**单元**？
- [ ] 如果整个链路中某一环坏了，我的测试能发现吗？
- [ ] 我有没有「依赖构建通过 / 静态分析通过」就给 PASS？（不能）

### 反例 vs 正例

```
❌ 前端 JS 改动：curl API 通过 → PASS  → 用户浏览器实际加载了旧 JS（缓存）
✅ 前端 JS 改动：headless 浏览器或人工验证 DOM 事件链路 + 检查 HTML 中所有 <script> 都带版本 token
```

## 原则间优先级

冲突时按以下顺序决策（左服从右）：

```
P-001（不问） < P-002（先定位） < P-003（升规则） < P-006（完整验证） < P-004（状态机） < P-005（资源同步）
```

**例**：用户催着发布（P-001 不问），但改动涉及共享接口（P-005）→ 仍必须 grep 所有调用点同步，不能跳过。

## 配套机制

### 经验库联动

违反任一原则导致的问题，写入 `lessons-learned.md` 时必须标注违反的原则编号：

```markdown
### EXP-NNN: {标题}

| 字段 | 值 |
|------|-----|
| 违反原则 | P-005（共享资源同步） |
| 域 | frontend |
| 类型 | anti-pattern |
| ... |

**原因**：...
**解法**：...
**预防**：下次按 P-005 步骤 1-4 执行
```

### 升规则触发

某条原则在项目中**反复被违反**（≥3 次）→ 应升级为项目专属规则，写入 `.claude/rules/project-specific.md`，作为编排时必注入的强约束。

### `/learn` skill 联动

`/learn` 扫描 lessons-learned.md 时，可统计每条原则的违反次数，提示用户哪些原则需要强化：

```
📊 原则违反统计（近 30 天）：
- P-005 共享资源同步：5 次（建议升规则）
- P-002 改动前先定位：3 次
- P-004 状态机完整性：1 次
```

## 与项目特定规则的关系

本文件**只放通用原则**（跨项目可复用）。

项目特定的业务规则（如「本项目用 Tailwind 不用 emotion」「本项目 DB 必须用 migration 工具」）写到 `.claude/rules/project-specific.md`，不要写进本文件。

主智能体编排时，两类规则一起注入 dev/tester agent prompt：

```
必须遵守的项目规则：
1. 通用原则（.claude/rules/principles.md）
2. 项目专属规则（.claude/rules/project-specific.md）
```
